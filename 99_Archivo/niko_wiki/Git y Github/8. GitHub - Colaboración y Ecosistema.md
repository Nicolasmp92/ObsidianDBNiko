# 🐙 GitHub: Colaboración y Ecosistema

GitHub no es solo un hosting de repos: es la capa social y de automatización sobre Git. Estas son las piezas que más usarás.

## 🔀 Pull Requests

La unidad de trabajo colaborativo: propones cambios desde una rama y otros (o tu CI) los revisan antes del merge.

- **Draft PR**: abre el PR antes de terminar para pedir feedback temprano.
- **Reviews**: comentarios por línea, aprobaciones y *requested changes*.
- **Estrategias de merge**:
  - `Merge commit` → conserva todo el historial de la rama.
  - `Squash and merge` → comprime la rama en un solo commit (historial limpio; ideal con [[6. Conventional Commits|Conventional Commits]]).
  - `Rebase and merge` → reescribe la rama sobre `main` (historial lineal).

## 🎫 Issues y Projects

- **Issues**: tareas, bugs y discusiones. Usa *labels* (`bug`, `enhancement`) y *milestones* para agrupar.
- Se cierran automáticamente desde un commit/PR con `closes #123`.
- **Projects**: tableros kanban nativos para priorizar issues y PRs.

## 🏷️ Tags y Releases

```bash
git tag -a v1.0.0 -m "Primera versión estable"
git push origin v1.0.0
```

- Un **tag** marca un punto del historial (normalmente con semver).
- En GitHub, *Releases* convierte el tag en una entrega: notas de versión + binarios adjuntos.

## 🍴 Forks

- **Fork**: copia del repo en tu cuenta para contribuir a proyectos ajenos (open source) sin permisos de escritura.
- Flujo: fork → clone → rama → push a tu fork → PR hacia el repo original.

## ⚙️ GitHub Actions

CI/CD integrado en el repo: workflows en `.github/workflows/*.yml` que corren en cada push/PR.

```yaml
# Ejemplo mínimo: correr tests en cada PR
name: tests
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./vendor/bin/phpunit
```

> [!TIP] Relación con tu flujo
> El pipeline ideal para tus proyectos: PR → Actions corre tests → merge con *squash* → tag de release. Ver [[4. Flujo de Trabajo Diario con Pull Requests]].
