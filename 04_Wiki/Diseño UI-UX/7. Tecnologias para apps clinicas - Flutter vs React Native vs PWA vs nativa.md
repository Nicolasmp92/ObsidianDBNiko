# Tecnologías para apps clínicas — Flutter vs React Native vs PWA vs nativa

> **Pregunta que responde esta nota:** para construir una app móvil de salud (agendamiento, notificaciones, fichas), ¿qué stack conviene y por qué Sconect eligió Flutter?
>
> **Respuesta corta:** la decisión se toma en dos filtros: (1) **¿necesitas app de verdad o te basta web?** — si el servicio funciona como sitio responsivo, una PWA es la ruta de menor compromiso; (2) si necesitas app, **cross-platform con UN codebase** (Flutter o RN) gana casi siempre sobre nativa para equipos chicos — nativa solo cuando la feature difícil (hardware, AR, tiempo real) es la fuente del valor. Para una app clínica standalone con UI controlada y equipo de uno: **Flutter**. El detalle abajo.

## 1. El mapa de opciones

| | **Nativa** (Swift/Kotlin) | **Flutter** (Dart) | **React Native** (JS/TS) | **PWA** (web instalable) |
|---|---|---|---|---|
| Codebases | 2 (una por plataforma) | 1 | 1 | 1 (es la web misma) |
| Render | Componentes del SO | Motor propio (Impeller) — pixel-idéntico en todos lados | Componentes nativos vía bridge/JSI | DOM del navegador |
| Acceso a hardware | Total, día 1 | Completo vía plugins/platform channels | Completo vía módulos nativos | Limitado (sin Bluetooth/NFC en iOS, background restringido) |
| Push notifications | Full | Full | Full | Sí, pero en iOS solo desde 16.4 y exige instalar al home screen |
| Distribución | Stores (review por release) | Stores | Stores (+ OTA para JS) | URL directa, **sin stores** — updates instantáneos |
| Costo relativo | El más alto (2 equipos) | Baseline | Baseline | ~30-50% menos |
| Mejor cuando… | La feature difícil (hardware, AR, real-time) ES el valor | UI controlada y consistente, app standalone, equipo chico | El equipo ya vive en React/TypeScript | El servicio se parece a un sitio responsivo: booking, contenido, autogestión |

## 2. El árbol de decisión

```
¿El servicio funciona como sitio web responsivo
y no exige capacidades del dispositivo?
│
├─ SÍ → PWA. Menor compromiso: URL, sin stores,
│        update instantáneo. Suficiente para
│        agendamiento, contenido, autogestión.
│
└─ NO (necesito app, push confiable, presencia
   en store, background, hardware)
   │
   ├─ ¿El valor está en una feature que exige
   │  hardware/OS al límite? → NATIVA (2 codebases,
   │  máximo control, máximo costo)
   │
   └─ ¿App de negocio/producto? → CROSS-PLATFORM
      ├─ equipo React/web → REACT NATIVE
      └─ app standalone + UI propia controlada
         + consistencia visual total → FLUTTER
```

## 3. Flutter: qué gana y qué paga

**Gana:**
- **Un codebase → iOS + Android + web + desktop** — para un equipo de uno es la diferencia entre viable e inviable.
- **Render propio (Impeller):** la UI se ve idéntica en un Samsung de gama baja y un iPhone — en salud, donde la audiencia usa hardware heterogéneo y viejo, la consistencia es accesibilidad.
- El vocabulario de diseño Material 3 está **implementado literalmente** (`Scaffold`, `NavigationBar`, FAB — ver [[3. Composicion de vistas moviles - anatomia de pantalla y donde va cada boton|entrada 3]]): diseñar y programar hablan el mismo idioma.

**Paga / riesgos a vigilar:**
- **Dart**: lenguaje menos común → curva inicial y menos reutilización de conocimiento JS existente.
- **Dependencia de plugins** para funciones nativas: cada plugin de terceros es una dependencia a auditar (mismo criterio de `interrogatorio-adopcion` — ya aplicado con `material_symbols_icons`).
- App store friction igual que cualquier app: cada release pasa review.
- Bundle base moderado (~15-30MB) vs PWA (<2MB).

## 4. Por qué Flutter para una app clínica tipo Sconect

1. **El producto es standalone** (no extensión de un sitio React existente) → no hay inercia JS que defender; Dart se absorbe como costo único.
2. **La audiencia exige consistencia** (adultos mayores, hardware variado — ver [[5. Accesibilidad en salud - disenar para adultos mayores y menor destreza digital|entrada 5]]): render propio = la UI cuidada en dev es la que recibe el paciente.
3. **El valor no es hardware** — es agenda, notificaciones y confianza → no justifica dos codebases nativas.
4. **Push confiable en ambas plataformas** sin los límites del PWA en iOS (donde push exige instalación y llegó recién en 16.4).
5. **Los recordatorios van por WhatsApp desde el backend** de todas formas → el canal crítico ni siquiera depende del cliente móvil, lo que hace aún más segura la elección.
6. Y honestamente: el equipo ya tenía el toolchain Flutter instalado y productos en él — el costo de cambiar excede cualquier ventaja teórica del resto.

**Cuándo revisar la decisión:** si el producto mutara a "solo agendamiento web sin app" → una PWA haría el 80% del trabajo por menos; si exigiera integración profunda con salud del SO (HealthKit/Google Health Connect en tiempo real, wearables) → evaluar módulos nativos o nativa pura.

## 5. Nota sobre "híbridas" (Ionic/Capacitor)

Existe una quinta vía — web code en WebView dentro de una app de store. Combina lo peor de dos mundos para este caso: paga la fricción del store sin ganar el rendimiento/look nativo. Útil cuando el equipo es 100% web y necesita presencia en store barata; no aplica aquí.

## Glosario mínimo

- **PWA:** sitio web instalable con service worker — se "instala" desde el navegador, sin stores.
- **Cross-platform:** un codebase que compila a varias plataformas (Flutter, RN).
- **Platform channel / bridge:** puente por el que el framework llama a APIs nativas del SO.
- **OTA update:** actualización del código JS sin pasar por review del store (Expo/RN).
- **HealthKit / Health Connect:** APIs de salud de iOS/Android — relevantes si el producto lee datos biométricos.
